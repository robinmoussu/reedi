Measuring the performance
=========================

The measurements use a generated repository matching the performance target of the README: 10
unpushed revisions of about 1000 changed lines each, always the same.

Tools
-----

On Arch Linux:

```
sudo pacman -S just perf time jq inferno valgrind kcachegrind heaptrack
paru -S hotspot
```

`just perf` and `just flamegraph` need `sudo sysctl kernel.perf_event_paranoid=1` (until the next
reboot), and say so when it is missing.

Measuring: the benchmarks
-------------------------

`just bench` runs the benchmarks of `benches/performance.rs`, which print the duration and the
allocations of:

- `startup`: what `reedi` computes before its first frame (loading the revisions, wrapping their
  rows, drawing the frame), at 80×24 and 200×50. Reading the settings and preparing the terminal
  are not included.
- `displayed_revisions`: loading the revisions.
- `rewrap`: wrapping the rows again (resizing, dragging the separator), at 80 and 200 columns.
- `frame`: drawing a frame (scrolling), at 80×24 and 200×50. Above 16 ms, scrolling is not fluid.

`cargo bench --bench performance -- frame` runs only the benchmarks whose name contains `frame`.

Comparing: before each commit
-----------------------------

`just compare [base]` displays the performance differences between the working tree and `base`
(default: `HEAD`). The working tree is measured if its results aren't saved yet; `base` too, after
asking `Build and measure <base>? [Y/n]`. `just measure [revision]` only measures `revision`
(default: the working tree).

A measurement builds `reedi` like the profilers do (below), from a `git archive` of the revision in
`target/performance/src/` unless it is the working tree, so that nothing is stashed, and keeps the
binary in `target/performance/bin/`. It runs on 2 generated repositories, generated by the working
tree's generator (so that any revision runs on the same input): without uncommitted changes, and
with both staged and unstaged changes. On each of them:

- `reedi`, on 200×50 and 48×24 terminals, opened, then 1000 `j` (every key drawn,
  `--draw-every-key`), then `q`, 5 runs, of which the median is kept: instructions, CPU time, wall time, peak memory (GNU `time`), time to the first
  full screen and longest refresh (`--timing`);
- the benchmarks, reading the repository from `$REEDI_PERFORMANCE_REPOSITORY`.

The results of each repository are saved in `target/performance/<key>.json`, with their identity:
the source (the tree of the revision, or of the tracked files of the working tree: amending only
the message of a commit keeps it), the repository (`HEAD`, `@{upstream}`, the index, the working
directory, the local git configuration) and the hash of `etc/measure.rs`. `<key>` is the hash of
that identity, so that a revision is measured once per repository, and `just compare` displays the
parts of the identities that differ.

`just compare` warns when a measure degrades by more than its threshold (instructions: 1 %; CPU
time, wall time, peak memory and the median time of a benchmark: 5 %) or exceeds a target of the
README (500 MB, 1 s to open, 200 ms to the first full screen, 500 ms to refresh), and then exits
with an error.

`just measure` and `just compare` run the cargo scripts `etc/measure.rs` and `etc/compare.rs`, which
need a nightly toolchain (`-Zscript`), and build them in `target/scripts`. Their tests run with
`cargo +nightly -Zscript test --manifest-path etc/measure.rs` (and `etc/compare.rs`).

`just install-hooks` makes git use `etc/hooks/`: its `commit-msg` hook displays the comparison of
a commit with its parent, with `etc/check.rs`, and refuses the commit if it warns, unless its
message has a `perf: <reason>` line. It also refuses a commit whose results or whose parent's
aren't saved (run `just compare` first).

Investigating: the profilers
----------------------------

Each target builds `reedi` with the `profiling` cargo profile (optimized, with symbols) and frame
pointers (in `target/frame-pointers`), creates the generated repository in
`target/performance-repository` if it is missing, runs `reedi` on it under the profiler, then opens
the report (written in `target/`) in its viewer.

By default, `reedi` replays the keys `99999jq` (to the last row, then quit), so that two runs do
the same thing. Other keys are written in Vim's key notation: `just perf '<C-d><C-d>q'`. With
`just perf ''`, you use `reedi` yourself and quit with `q`.

| Target | Measures | Viewer | Use it to |
|---|---|---|---|
| `just perf` | CPU time, sampled | Hotspot | find which functions take the time |
| `just flamegraph` | the same | a flamegraph (SVG) in the browser | see at a glance where the time goes |
| `just callgrind` | instructions executed, exactly (tens of times slower) | KCachegrind | compare two versions: the counts don't vary between runs |
| `just heaptrack` | allocations and memory | `heaptrack_gui` | find what allocates, and the peak memory |

`just flamegraph` takes one to two minutes to find the functions inlined by the compiler.

`perf` only samples while `reedi` runs on a CPU: waiting (for the terminal, for instance) is
invisible. Hotspot can record it too, with its off-CPU profiling option.

`just generate <directory>` creates the generated repository elsewhere, to run `reedi` on it by
hand.
